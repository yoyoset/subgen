# subgen 技术评审报告(2026-07-23)

> 评审角色:桌面/工具类软件产品负责人兼技术评审人。基于当时仓库全部源码(约 3800 行)与 README 的实际阅读,非通用泛谈。

## 总体评估

项目实际成熟度远高于作者自述:界面、设置、容错、进度反馈、断点续跑、进程生命周期管理(Job Object)、哈希校验、针对真实故障的回归测试都已存在且质量相当高——"子进程调用预编译二进制、不碰 FFI/CUDA 工具链"是架构里最正确的决定,一次性绕开了本地模型类工具 80% 的分发深坑。当前最大风险不在功能缺失,而在三处:**仓库一次 commit 都没有**、**ffmpeg 用无版本号滚动链接**(上游一改布局所有新用户装不上)、**大模型下载不支持断点续传**(4GB 文件网络一抖从零重来)。

## 0. 技术栈评估

**结论:选型合适,不建议换。**

- Rust + egui:对"批处理队列 + 进度条 + 设置项"的工具形态完全够用且有优势(单文件 exe、无 webview/Node 依赖)。Tauri 只在要做复杂字幕编辑器时才值得考虑。
- 子进程调用 whisper.cpp / llama.cpp / ffmpeg 预编译二进制:优于 whisper-rs 等 FFI 绑定——构建机不装 CUDA 工具链、升级引擎只是换 zip、崩溃隔离在子进程。保持。
- 常见坑已踩过并修复:静默 CPU 回退检测、子进程弹控制台、孤儿进程、复读死循环、CUDA DLL 复用。
- 遗留风险:
  - **wgpu"设备丢失直接 panic"**(实际发生过,与 whisper/llama 抢 GPU 时触发)。建议 `NativeOptions` 切 `Renderer::Glow`,glow 对设备丢失容忍度远高于 wgpu,此 UI 用不到 wgpu 能力。**P0**(有真实崩溃案例)。
  - 只覆盖 NVIDIA:whisper.cpp / llama.cpp 官方有 Vulkan 预编译包,可作 AMD/Intel 用户第二档。**P2**。
  - CUDA 12.4 预编译包要求 NVIDIA 驱动 ≥ 551.x,老驱动静默掉 CPU;GPU 检测能兜住,错误提示可加"或驱动版本过旧"。**P2**。
- 流程层面 P0:**先 `git add -A && git commit`**,仓库当前零提交,3800 行代码无任何版本保护。

## 1. 性能

- 瓶颈排序:ASR(large-v3,约 8 倍实时)≥ 翻译 >> 音频提取 >> 排版。
- **下载无断点续传**(setup.rs 无 Range 请求)。Sakura 4.25GB、large-v3 2.9GB,是首次安装失败率最大来源。改法:下载到 `.part`,失败后 `Range: bytes=N-` 续传,哈希校验不变。**P0**。
- **显存竞争降级缺失**:8GB 卡开翻译时 llama-server 常驻 + whisper 启动的重叠窗口大概率 OOM;llama-server 启动失败已优雅降级,但运行中 OOM 未处理。建议启动前用 `nvidia-smi --query-gpu=memory.total,memory.free --format=csv` 探测,< 10GB 改"串行模式"(每文件翻译完 stop llama-server 再跑下一个 whisper)。**P1**。
- **翻译阶段无 GPU 检测**(作者已知 TODO):llama-server 日志只排空不解析,掉 CPU 后 7B 模型每批 15 行可能逼近 120s 超时,触发对半重试雪崩。解析 stderr 里的 CUDA/offload 行(如 `offloaded N/N layers to GPU`),接入现有 `GpuMissing` 警告通路。**P1**。
- 请求加 `"cache_prompt": true`:system prompt 每批相同,KV 缓存复用是白捡的速度。**P2**。
- 流水线并行(下个文件 ffmpeg 与当前 whisper 重叠):收益小,**P2**。GPU 并发识别不值得,现有判断正确。
- 超长文件分段:`-mc 0` 已消除跨窗口状态,理论可行,但收益不大。**P2**。

## 2. 界面/交互

- **批次结束无汇总**:跑完 20 个文件无"18 成功 / 1 跳过 / 1 失败,总耗时 47 分"收尾,失败项要自己找。加汇总 + 失败项置顶/过滤。**P1**。
- **结果无出口**:完成后无"打开所在文件夹"/"打开字幕文件"入口。每行加小按钮。**P1**。
- 列表管理:不能移除单个条目、处理中不能追加文件(可追加到队尾)。**P2**。
- 字幕预览/抽检:完成后可看前 N 条译文对照;egui ScrollArea 只读预览没问题。**可编辑**字幕编辑器是 egui 能力边界起点(中文 IME 在 TextEdit 历史问题不少),编辑需求出现时优先"调用系统默认编辑器打开 srt"。**P2**。
- egui 边界:无原生菜单/托盘/任务栏进度;Windows 任务栏进度可用 `windows` crate 调 ITaskbarList3,长任务工具很值。**P2**。

## 3. 设置项

现有暴露(whisper 模型、源语言、覆盖策略、翻译开关/模型/双语、模型目录)克制且默认值合理。补充:

- 翻译目标语言硬编码中文:用户画像即中文用户则保持现状。**P2(仅当有需求)**。
- **输出格式仅 srt**:ass(样式/字号/描边)对双语字幕观感提升明显——中文大字原文小字是刚需级排版,是"排版处理"维度最值得做的一件事。**P1**。
- **排版规则**(每行最大字数/自动断行/最短显示时长):whisper 单条字幕有时很长。加后处理(超长在标点处断行、合并 <300ms 碎片),默认开启。**P1**。
- tmp/logs 清理:成功后中间 srt 和 logs 持续积累,加清理按钮或"保留最近 N 天"。**P2**。
- 高级项(线程数、`-ng`、BATCH_SIZE、端口):折叠"高级"区或仅 config.toml 手改。**P2**。
- 小 bug:`Config::load` toml 解析失败 `unwrap_or_default()` 静默丢弃用户全部配置,至少 UI 提示"配置文件损坏,已重置"。**P2**。

## 4. 流程细化与容错

做得最好的维度(阶段化错误、对半重试、Job Object、断点续跑、退出码十六进制记录)。剩余缺口:

- **双语模式下翻译失败行输出两遍原文**:失败时把原文当译文返回,双语拼接 `{zh}\n{orig}` 变成同一句原文重复两行。失败行在双语模式应只输出一遍原文。**P1**(简单修,用户可见瑕疵)。
- **无单实例保护 + 固定端口 8712**:开两个 subgen 共用 tmp/、抢端口,第二实例翻译引擎启动必失败且报错误导向"显存不足"。用已引入的 fs4 做文件锁。**P1**。
- 断点续跑恢复语言失败时:`detected_language` 退化 "auto" → `pick_model` 兜底 Qwen——日语视频续跑后可能悄悄从 Sakura 换成 Qwen,质量下降无感知。警告提示或轻量假名检测。**P2**。
- 取消时删除 wav 和半成品 srt:"取消"比"崩溃"损失更大。取消时保留完整的 wav,只删半成品 srt。**P2**。
- **日志碎片化**:setup/迁移/翻译事件只在 UI `log_lines`,关窗即失。加追加式 `logs/app.log`,用户报障"把 logs 文件夹发我"才成立。**P1**。

## 5. 用户反馈机制

- **批次汇总报告**(与界面维度一体实现):结束时可选导出文本报告(每文件:耗时/检测语言/所用模型/失败行数/警告)。**P1**。
- 翻译质量抽检:警告区显示"共翻译 N 行,M 行未对齐保留原文",点开可看是哪些行。**P2**。
- **长任务结束提醒**:`ViewportCommand::RequestUserAttention` 闪任务栏,一行代码。**P1**(性价比极高)。

## 6. 提示词优化

- **跨批上下文携带**:现在每批 15 行独立翻译,人称/称呼/术语在批边界漂移。改法:user 消息附前一批最后 2~3 行原文+已定译文,标注"仅为上下文,不要重复输出"。对齐解析不用改。**P1**,翻译质量最便宜的显著提升。
- 术语表:视频同目录放 `{名字}.glossary.txt`(每行 `原文=译文`),存在即注入 system prompt,不做 UI。**P2**。
- 字幕长度约束:提示词加"译文务必简洁,单行不超过 N 字",配合排版后处理。**P2**。
- Sakura 编号格式偏离官方单段格式:花半小时 A/B(同一集,BATCH_SIZE=15 vs 3),把"如果质量下降再调"变成已验证结论。**P2**。

## 7. 依赖与分发

"首次运行下载、组件不进安装包"的取舍正确,保持。缺口:

- **ffmpeg 滚动链接无版本无哈希**:唯一"上游打喷嚏、所有新用户装不上"的单点。换 gyan.dev 带版本号 release 或 BtbN GitHub Release 固定 tag,补哈希。**P0**。
- **下载断点续传**:**P0**。
- **国内网络可达性**:GitHub Release 和 HuggingFace 对大陆用户经常半残。加镜像回退(HF → hf-mirror.com 换域名;GitHub → ghproxy 类前缀),官方失败后自动尝试。**P1**(视用户画像,可能是 P0)。
- SmartScreen/杀软误报:无签名 exe + 运行时下载 exe + 起子进程是杀软启发式完美靶子。现实做法:README 写明预期提示、zip 分发、VirusTotal 链接自证。**P2**。
- 自动更新:**P2** 甚至不做——绿色软件"下载新 zip 覆盖"可接受;先把版本号显示在标题栏。

## 完善路线图

**第一阶段(P0,一两个晚上量级)——消除"会烧起来"的风险:**
1. `git init` 后首次提交,保持提交习惯
2. ffmpeg 换固定版本 URL + 哈希校验
3. 大文件下载断点续传(Range + .part)
4. eframe 渲染后端切 Glow,消除已发生过的 wgpu 崩溃

**第二阶段(P1,约一周)——从"能跑"到"好用":**
5. 翻译阶段 GPU 检测(解析 llama-server 日志,接入现有警告通路)
6. 显存探测 + 低显存串行降级模式
7. 双语模式失败行重复输出修复 + fs4 单实例锁
8. 批次结束汇总 + 任务栏闪烁提醒 + 每行"打开文件夹"按钮
9. 持久化 app.log
10. 翻译跨批上下文携带(质量提升性价比之王)
11. 排版后处理(断行/最短时长)+ ass 双语样式输出
12. (若面向大陆用户)HF/GitHub 镜像回退——可升 P0

**第三阶段(P2,按兴趣排期):**
13. 术语表注入、Sakura 批大小 A/B、字幕长度约束提示词
14. 字幕预览/未对齐行查看、单条目移除、处理中追加队列
15. Vulkan 后端支持非 N 卡、tmp/logs 清理、配置损坏提示
16. GitHub Actions 跑 `cargo test`
