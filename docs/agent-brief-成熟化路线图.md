## 二、纪律(门槛,不是建议)

**1. 先实测再下结论。** 这个项目已发生 4 次"读文档/读源码/凭印象≠验证过运行时"的
事故:号称"源码实测确认"的日志格式在真实二进制里根本不存在;凭标准库印象用路径函数
导致成功却报错;拆分重构时凭记忆重写代码引入类型和标点错误;分析脚本读文件的方式和
被分析代码不一致,算出荒谬数字差点当成重大发现。
→ 涉及"某函数/某日志/某第三方工具的具体行为",先写最小复现真跑一遍。搬代码用
`sed`/脚本机械提取,不凭记忆重打。**结论异常到"这不太可能"时,先怀疑自己的验证方式。**

**2. 提交纪律。** 逻辑独立的改动单独 commit;`cargo build --release`(零警告)+
`cargo test`(全绿)+ `cargo clippy --all-targets`(零警告)三项全过才提交;commit
message 写具体数字/复现步骤,不写"优化""修复"。跑真实文件的临时 `#[ignore]` 测试
看完即删,不入库。

**3. 范围纪律。** 不为"以后可能需要"过度设计,三行相似代码好过过早抽象。每次改动
明确写"这次不做什么"和理由。**做完一项就停下汇报,不要闷头做完整张清单**——你是
自主运行的,没人实时盯着,更需要主动设检查点。

**4. 这是 Windows-only 绿色便携软件。** 路径相对 exe 目录,不写注册表、不装系统目录。
外部二进制和模型是运行时按需下载的独立组件(`src/setup/`),要碰先读完现有实现。
真实测试素材在 `E:\` 盘(如 `E:\season 11`,已是双语字幕),不在项目目录里。

**5. 必须停下来问,不能自己拍板:** 删除/覆盖用户真实数据;依赖真实模型推理才能验证
正确性的改动;改变用户可见行为或 UI 交互;Git 破坏性操作(force push / reset --hard /
删分支);**以及任何你觉得"可能不对但不确定"的时候——不确定本身就是要问的信号。**
